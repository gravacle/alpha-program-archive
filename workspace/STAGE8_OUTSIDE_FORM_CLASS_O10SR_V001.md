## 4. DELIVERABLE (3) — THE POSABILITY TEST

The commission's distinction, restated before it is applied, because everything
turns on it: a type is **INADMISSIBLE** when the site could receive a
certificate of that type but a rule refuses it. A type is **UNPOSABLE** when the
site's demand is itself phrased so that no certificate of that type is even a
well-formed candidate — there is no substitution instance to refuse. An
unposable demand is the deeper finding, because no rule act repairs it: the
demand would have to be **re-stated**, not re-permitted.

### 4.1 The test, stated before it is applied

```text
THE TEST.  Take the site's demand at its own bytes.  Ask: is the demand
  (A) an ORDER RELATION whose relata are magnitudes — a bound, a majorant, a
      rate, an inequality — in which case a candidate must be a magnitude, and
      an invariant valued in a sign group, a kernel-membership, or an
      incidence datum has NO substitution instance; or
  (B) an EXHIBITION — a demand that some object be DISPLAYED on a named
      structure — in which case any object of the named kind is a well-formed
      candidate and the question of admissibility can arise at all?
  (A) => UNPOSABLE for non-analytic types.  (B) => POSABLE; admissibility
  then becomes a real, separate question.
```
